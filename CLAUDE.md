# CLAUDE.md — Datathon 26: нарушения кассовой дисциплины по видео

## Что строим
Локальный AI-сервис для ForteBank: пользователь загружает видео работы кассира, сервис находит
визуально наблюдаемые признаки возможных нарушений и для каждого выдаёт тип, таймкод,
1–3 кадра-доказательства, описание и ссылку на пункт нормативного акта РК.
Результат — подсказка проверяющему, а не юридическое заключение.

**Источник истины — ТЗ кейса ForteBank с FAQ (PDF у команды; ссылки «FAQ N» ниже — на него).**
При расхождении с этим файлом право ТЗ, а этот файл нужно обновить.

## Жёсткие ограничения (нарушать нельзя никогда)
- **Только локально.** Все модели работают внутри нашего сервиса. Запрещены любые облачные AI:
  OpenAI, Anthropic API, Gemini, Azure Vision, AWS Rekognition, HF Inference API, Plate Recognizer и т. п.
  Нельзя отправлять наружу видео, кадры или их текстовые описания.
- **Офлайн после загрузки весов.** Обработка видео не должна ходить в интернет. Веса скачиваются
  заранее скриптом `scripts/download_weights.py` и лежат в `weights/`. В рантайме никаких
  `from_pretrained` с загрузкой из сети: только локальные пути, `HF_HUB_OFFLINE=1`.
- **5 минут на видео.** Цель — укладываться в 3 минуты на типичном ролике с запасом.
- **Не утверждать невидимое.** Если для вывода нужны данные, которых нет на видео (проводки,
  сверка, АБИС, журналы), событие не выдаётся как нарушение.
- **Не выдумывать нормативку.** Ссылки на правила берутся ТОЛЬКО из `rules/norms.yaml`.
  Генерировать номер документа или пункта «из головы» запрещено. Только акты РК (НБРК, adilet.zan.kz).
- **Не распознавать и не идентифицировать лица** (FAQ 29). Люди — только как «кассир», «клиент»,
  «инкассатор», «посторонний».
- **Только визуальный анализ, без звука** (FAQ 28).
- **Лицензии.** Модели и код — только open source с лицензией, разрешающей коммерческое
  использование (FAQ 24). Например, AGPL (ultralytics YOLO) — проверить перед сдачей.
  Готовые сторонние решения и облачные API — дисквалификация (FAQ 35).
- **Тестовые видео жюри** нельзя использовать для обучения, публиковать или передавать третьим лицам.

## API (строго по ТЗ, не менять формат)
- `POST /api/v1/analyze` — multipart, поле `file`, формат `.mov`. Ответ: `{"job_id": "..."}`.
- `GET /api/v1/jobs/{job_id}` — `status`: `processing` | `done` | `failed`.
- Авторизация: заголовок `X-API-Key`. Без верного ключа — 401. Ключ из env `API_KEY`.
- Ответ при `done`:
```json
{
  "job_id": "3f2a9c1e",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Название типа нарушения",
      "timecode_sec": 44.2,
      "description": "Что видно на видео и почему это может быть нарушением",
      "evidence_frames": [{ "timestamp_sec": 44.2, "image_base64": "/9j/4AAQ..." }]
    }
  ]
}
```
- `verdict`: `no_violation` (violations = []) или `violation`.
- `evidence_frames`: от 1 до 3 кадров, JPEG, base64 без префикса `data:`.
- Оценка автоматическая по этой JSON-схеме (FAQ 18): в ответ `/jobs/{id}` доп. поля НЕ добавляем.
  Данные для UI (уверенность, интервал, цитата нормы, прогресс) отдаются отдельными эндпоинтами
  `/jobs/{id}/details`, `/jobs/{id}/progress`, `/norms`, `/ml/health`, `/feedback`, `/feedback/export`.
- Отзывы проверяющих (`storage/feedback/`) — датасет для дообучения. Отзывы с `trainable: false`
  (в т. ч. на видео жюри) в обучение не брать.
- `timecode_sec` — секунды от начала видео; указывать конкретный кадр и таймкод (FAQ 17).
- Нет результата за 5 минут или сервис недоступен — видео считается необработанным.
- Сервис обязан принимать `.mov` около 29 МБ (FAQ 25). Нужен публичный URL (FAQ 23).
- Есть контрактный тест `tests/test_api_contract.py`: запускать после любых правок API.

## Типы нарушений: `rules/violation_types.yaml`
- Закрытого списка нет; в тесте могут быть типы, которых нет в обучающих данных (FAQ 8–9).
  Датасет размечен только «нарушение + таймкод», тип определяем сами (FAQ 2).
- Каждый тип: `id` (V01…), `key`, `type` (название в API), `criterion` (визуальный критерий),
  `norms` (id из norms.yaml), `status` (`черновик` | `подтверждён`), `template` (шаблон описания).
  Невидимые по видео случаи — в разделе `excluded`.
- `type`, который отдаёт ML-сервер, должен совпадать с `type` в этом файле: по нему бэк подставляет норму.
- Тип выдаётся в API только после подтверждения примерами из датасета и пунктом нормативки
  (`status: подтверждён`).
- Нарушения «по бездействию» (не сделал обязательное действие): таймкод — на усмотрение команды (FAQ 10),
  но только если отсутствие действия видно на видео, а не выводится из невидимых данных.

## Нормативная база: `rules/norms.yaml`
```yaml
updated_at: "YYYY-MM-DD"          # дата обновления базы (показывается в UI)
documents:
  DOC_231:
    title: "Полное официальное название акта"
    approved_by: "кем и когда утверждён, номер"
    edition: "ред. на ДД.ММ.ГГГГ"
    url: "https://adilet.zan.kz/..."
norms:
  - id: N231_20_2                 # N<номер постановления>_<пункт>[_<подпункт/часть>]
    doc: DOC_231
    clause: "п. 20 ч. 2 (гл. 2, параграф 2)"
    quote: "дословная цитата пункта"
    note: "(опц.) особенности применения/редакции"
    source_checked: "где сверен текст"
    adilet_checked_at: "YYYY-MM-DD"   # дата сверки на adilet.zan.kz
```
- Связь «норма → тип нарушения» хранится только в `violation_types.yaml` (поле `norms`).
- Источники: только акты РК — adilet.zan.kz, сайт НБРК (FAQ 30). Только действующие редакции.
- Ссылка без точного пункта допускается (FAQ 31), но если цитату не удалось найти дословно — пункт не используем.
- Норма должна соответствовать наблюдаемому действию: жюри оценивает точность источника и трактовки
  (критерий 4, 15 баллов).
- В описании нарушения формулировка «может указывать на нарушение п. X», а не «нарушен закон».

## Пайплайн
**Сейчас:** модели (Qwen3-VL-8B + LoRA-адаптер + детектор предметов) работают на GPU-сервере команды
как ML-сервер (порт 8001). Бэк отправляет видео на `POST {ML_URL}/infer` (поле `file`, заголовок
`X-ML-Token`, таймаут 280 с) и получает `verdict` + `violations` в формате ТЗ; `job_id` и `status`
добавляет бэк (`backend/pipeline/remote.py`). `ML_URL` и `ML_TOKEN` — в `.env`.
Для жюри бэк запускается на том же GPU-сервере (`ML_URL=http://localhost:8001`), наружу через туннель
открыт только порт 8000: видео не уходит с сервера по пути к моделям.

**Запасной локальный пайплайн** (`pipeline/model.py`, `events.py`; работает без `ML_URL`, сейчас заглушки):

1. Декодирование видео (ffmpeg/PyAV), сэмплинг 2–5 fps, сохраняем реальные timestamp кадров.
2. Детекция и трекинг: люди, руки, деньги/пачки, сейф/ящик, телефон и т. п. (модель — на выбор ML-команды).
3. Состояние сцены во времени: кто в зоне кассы, где деньги, открыто ли хранилище, есть ли кассир рядом.
4. Правила-детекторы по состоянию сцены дают кандидатов событий с интервалом [start, end].
5. Перепроверка кандидатов локальной VLM на нескольких кадрах интервала (отсекает ложные).
6. Слияние близких событий одного типа, выбор лучшего кадра, таймкод = момент наибольшей уверенности.
7. Описание собирается из фактов (что, где, сколько секунд), без домыслов.

Все пороги и параметры — в `config.yaml`, не хардкодить.

## Описание нарушения (description)
- Только наблюдаемые факты: «Кассир отходит от рабочего места, пачка купюр остаётся на столе 38 с».
- Затем связь с правилом: «Это может указывать на нарушение требования …».
- Запрещено: догадки о намерениях, о суммах, о том, чего не видно на кадре, «нарушен закон»,
  «требуется проверка» вместо связи с правилом.
- Описание без неподтверждённых предположений (ТЗ, раздел 5).

## Валидация и метрики
- Делить данные по видео, не по кадрам. Отдельно держать ролики с другим ракурсом: финальное видео
  жюри снято под другим углом (FAQ 4), устойчивость — отдельный критерий.
- Данные: постановочные, вид сверху, одна камера, одна касса; в кадре кассир, клиенты, инкассаторы (FAQ 3).
  Дополнять датасет своими съёмками и синтетикой можно (FAQ 7).
- Скрипт `scripts/evaluate.py` считает метрики под критерии жюри:
  - вердикт по видео (accuracy, precision, recall);
  - точность таймкода (|Δt| ≤ 2 с / ≤ 5 с);
  - точность типа нарушения;
  - время обработки на видео.
- После каждого изменения модели или порогов — прогон `evaluate.py` и сравнение с прошлым результатом
  в `reports/`.
- **Пропуск нарушения недопустим, ложных срабатываний — как можно меньше** (FAQ 16): сначала высокий
  recall по вердикту, затем снижаем ложные срабатывания, не теряя recall.
- Критерий 1 (25 баллов) считается по вердикту на всё видео (FAQ 15).

## Как работать в этом репозитории
- Сначала смотреть на данные: перед изменением логики открыть кадры проблемных роликов.
- Разбор ошибок: для каждого FP/FN сохранять кадры с отрисованными детекциями в `reports/errors/`.
- Если задача повторяется (прогон валидации, разбор ошибок, проверка API) — предложить оформить её
  как скилл через /skill-creator.
- Стек: Python 3.11, FastAPI, фоновая очередь задач, Docker с GPU. Фронт — простой, с плеером и
  таймлайном меток.
